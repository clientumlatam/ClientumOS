The application uses a layered environment configuration system built around `.env` files, the `dotenv` package, and custom Node.js scripts for bootstrapping, synchronization, and secret management across multiple deployment targets (Replit, Vercel, GitHub Actions).

**Loading mechanism**: The Express server (`server.ts`) calls `dotenv.config()` at startup to load variables from `.env`, `.env.local`, and the process environment. All runtime configuration is accessed via `process.env.*` — there is no centralized config object or typed configuration module.

**Configuration sources and precedence**:
- `.env.example` — canonical template listing all required variables with comments describing each one
- `.env` — generated by `scripts/setup-env.js` (interactive) or `scripts/generate-env.mjs` (non-interactive), containing actual values
- `.env.local` — generated by `scripts/pull-secrets.mjs` from Vercel, used for local development overrides
- Process environment variables — highest precedence, picked up automatically by Node.js

**Bootstrap scripts**:
- `scripts/setup-env.js` — interactive wizard that guides developers through acquiring credentials (Gemini API key, SMTP, Neon DB, etc.), validates placeholder values, and writes a documented `.env` file with inline descriptions and acquisition links
- `scripts/generate-env.mjs` — non-interactive variant that auto-populates missing keys with deterministic defaults (e.g., random session secrets, CRM tokens)
- `scripts/pull-secrets.mjs` — pulls encrypted env vars from the Vercel project API (`/v9/projects/{id}/env?decrypt=true`) into `.env.local`, filtering out platform-specific keys and handling sensitive variable types
- `scripts/sync-secrets.mjs` — bidirectional sync tool that pushes Replit secrets to both Vercel env vars and GitHub Actions secrets, with a `--dry-run` mode and explicit mapping between source and destination key names

**Key configuration categories**:
- Database: `DATABASE_URL`, `NEON_DATABASE_URL`, `NEON_API_KEY`, `NEON_PROJECT_ID`
- Authentication: `SESSION_SECRET`, `CRM_INTERNAL_TOKEN`, `SANTI_API_KEY`
- AI services: `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `OPENROUTER_API_KEY`, `GROQ_API_KEY`
- External APIs: `HUNTER_API_KEY`, `APIFY_API_TOKEN`, `GOOGLE_MAPS_PLATFORM_KEY`
- Email: `SMTP_USER`, `SMTP_PASS`
- App behavior: `APP_URL`, `PORT`, `NODE_ENV`

**Conventions observed**:
- Every secret has a corresponding entry in `.env.example` with a comment describing its purpose
- Placeholder detection treats values like `MY_*_KEY`, empty strings, and strings containing "placeholder" as invalid
- Production vs development behavior is controlled via `NODE_ENV` (affects SSL cookie flags, database connection options)
- Sensitive variables are stored as encrypted secrets in Vercel and GitHub Actions rather than plaintext
- The setup scripts detect CI environments (`process.env.CI`) to disable interactive prompts
- Missing or unconfigured dependencies gracefully degrade (mock pgPool, memory session store, local Gemini fallback)
